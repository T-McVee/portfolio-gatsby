## Critical Pitfalls

### Pitfall 1: Contact Form Appears Functional But Never Delivers Messages

**What goes wrong:**
The contact form submits successfully, the user sees a "thank you" state, and every smoke test passes — but no emails are ever sent. `/api/contact/route.ts` currently only `console.log`s submissions. A deployed site with this code is silently dropping every contact attempt.

**Why it happens:**
The API stub was scaffolded during the migration to preserve the form contract. It's easy to defer "wire up the email service" because the UX looks finished. Once deployed, the failure is invisible — there are no error logs visible to the site owner, and users have no indication anything is wrong.

**How to avoid:**
Before deploying to a live domain, integrate Resend (or equivalent). The `RESEND_API_KEY` must be added as an App Service environment variable (not committed to the repo). Use Zod to validate the request body on both client and server. Add server-side error handling so failures return a non-200 response that the frontend can surface to the user.

**Warning signs:**
- `/api/contact/route.ts` contains `console.log` but no outbound HTTP call to an email provider
- No `RESEND_API_KEY` (or equivalent) in App Service configuration
- Form clears on network error instead of preserving the message (existing bug in `PageClient.tsx`)

**Phase to address:**
Contact form integration phase (before any live deployment or domain cutover).

### Pitfall 2: Deploying the Orphaned Static Web Apps Workflow to an App Service Target

**What goes wrong:**
The existing `.github/workflows/azure-static-web-apps-happy-wave-0b97bea00.yml` was created for Azure Static Web Apps and sets `output_location: "public"`. This is wrong for Azure App Service, which requires running the Next.js server process (`next start`), not serving a static export from `public/`. Pushing to `master` with this workflow could deploy an incomplete or empty build to the wrong Azure resource.

**Why it happens:**
The workflow was auto-generated by Azure when the original Gatsby site was connected to Static Web Apps. The migration changed the deployment target to App Service but the workflow was never updated. It's easy to miss because the file is in `.github/workflows/` and not part of the application code reviewers focus on.

**How to avoid:**
Delete the Static Web Apps workflow file entirely. Create a new GitHub Actions workflow that:
1. Runs `npm ci && npm run build`
2. Uses the `azure/webapps-deploy` action (not `Azure/static-web-apps-deploy`)
3. Zips the Next.js build output (`.next/`, `public/`, `package.json`, `package-lock.json`, `next.config.ts`)
4. Deploys to the App Service slot
5. App Service startup command must be set to `node_modules/.bin/next start` or `npm run start`

**Warning signs:**
- Workflow uses `Azure/static-web-apps-deploy@v1` action
- `output_location: "public"` is set (correct for static export, wrong for server-rendered Next.js)
- Deployment secrets reference `AZURE_STATIC_WEB_APPS_API_TOKEN_*` (Static Web Apps token, not an App Service publish profile)

**Phase to address:**
CI/CD setup phase — this is the first thing to fix when setting up deployment automation.

### Pitfall 3: Next.js App Service Deployment Produces Blank Page or 404 Due to Missing Startup Command

**What goes wrong:**
The Next.js app builds successfully, deploys to Azure App Service, and the deployment logs show success — but the live URL returns a blank page, 404, or "Application Error" because App Service doesn't know how to start a Next.js server. It defaults to looking for a static `index.html`, which doesn't exist.

**Why it happens:**
Azure App Service (Node.js) requires an explicit startup command to run the server. Unlike Static Web Apps (which serves pre-built files), App Service needs to execute `next start` as its entry point. This is configured separately in the App Service resource, not in the deployment workflow, and is easy to miss if you're focused on the GitHub Actions side.

**How to avoid:**
In the Azure App Service resource:
- Set the startup command to `npm run start` (which maps to `next start`)
- Ensure `NODE_ENV=production` and any other required env vars (`RESEND_API_KEY`, etc.) are set in Configuration > Application Settings
- Set `SCM_DO_BUILD_DURING_DEPLOYMENT=false` if deploying a pre-built artifact (which is preferred for Next.js)
- Use `PORT` env var or ensure `next start` binds to the port App Service expects (default: 8080 for Linux App Service; Next.js default is 3000 — configure with `next start -p 8080` or set `PORT=8080`)

**Warning signs:**
- App Service logs show the Node process exiting immediately after deploy
- Live URL returns a generic Azure error page
- No startup command configured in App Service Configuration blade
- `next start` defaults to port 3000 but App Service expects 8080

**Phase to address:**
CI/CD setup phase — verify startup command and port binding before first deployment.

### Pitfall 4: Stale Contentful Credentials Left in Environment Files

**What goes wrong:**
The `.env.development` and `.env.production` files at the project root contain Contentful API credentials that are no longer used. While these files are `.gitignored` and not in the repository, they still exist on disk and could be inadvertently committed if the `.gitignore` is modified, or leaked if the developer's machine is compromised.

**Why it happens:**
Migrations leave artifact credentials in place because removing them feels like a risky "clean up later" task. Since the `.gitignore` prevents the immediate problem (secrets in the repo), the urgency dissipates.

**How to avoid:**
Delete `.env.development` and `.env.production` from disk. Create a `.env.example` file documenting the variables actually needed for the current codebase (`RESEND_API_KEY`). This also serves as documentation for future contributors.

**Warning signs:**
- `.env.development` or `.env.production` files exist at project root
- Files contain `CONTENTFUL_*` or other service credentials no longer in use
- No `.env.example` documenting current required vars

**Phase to address:**
Content refresh / setup phase — clean up before adding real secrets for email service.

### Pitfall 5: Content Refresh Creates Silent Build Breaks (JSON/MDX Fragility)

**What goes wrong:**
A content update — editing `skills.json`, adding a new `.mdx` file, or modifying frontmatter — causes a build failure or runtime crash with no clear error message. The hand-rolled MDX frontmatter parser in `content.ts` fails silently on edge cases (multiline values, colons in strings, special characters). The unguarded `JSON.parse()` calls throw uncaught exceptions on malformed JSON.

**Why it happens:**
Content updates feel low-risk because they're "just data" not code. But the parsing layer has no input validation or error boundaries. The custom parser was built for simple key-value frontmatter and will fail on anything more complex. `JSON.parse()` crashes the entire server response if any file has a syntax error.

**How to avoid:**
Before refreshing content at scale:
1. Wrap all `JSON.parse()` calls in try-catch with error messages that include the file path
2. Add `gray-matter` to replace the hand-rolled frontmatter parser — it handles edge cases correctly
3. Add Zod schemas to validate parsed content matches `Project`, `Skill`, `ContactMethod` types at runtime
4. Verify content schema by running `npm run build` locally after every content change before pushing

**Warning signs:**
- `content.ts` lines 8-12, 16-17, 24-26 use bare `JSON.parse()` without try-catch
- `parseMdx()` function uses regex/string splitting instead of a proven YAML parser
- No build-time type validation for content files
- Build failure with cryptic "Cannot read properties of undefined" errors after a content edit

**Phase to address:**
Content refresh phase — harden the parser before updating any content files.

### Pitfall 6: Tailwind v4 Dynamic Class Generation Breaks Styles in Production

**What goes wrong:**
Component styles that work perfectly in development disappear in the production build. Conditionally-constructed class strings (`array.join(" ")`, template literals with variable interpolation) are not detected by Tailwind's class scanner at build time, so the CSS is never generated. The page renders without the expected styles.

**Why it happens:**
Tailwind v4's scanner works by statically analysing source files for complete class name strings. If a class is assembled dynamically — e.g., `["text-", size].join("")` or `` `bg-${color}-500` `` — the scanner cannot detect it and excludes it from the output CSS. In development, this is masked because all classes may be present from other usages.

**How to avoid:**
Use complete, static class strings in all conditionals. The correct pattern is:
```typescript
// Correct
const cls = isActive ? "bg-blue-500 text-white" : "bg-gray-200 text-gray-800"

// Wrong
const cls = `bg-${isActive ? "blue" : "gray"}-500`
```
Use `clsx` or `cn` utility for conditional composition of complete class names. Avoid `.join()` on partial class strings. The HANDOVER.md already flags this pattern specifically.

**Warning signs:**
- Class strings assembled with array `.join()` or template literals containing variables
- Styles present in development that disappear after `npm run build`
- `src/components/work/Project.tsx` lines 48-60 already identified as using this pattern

**Phase to address:**
Styling polish phase — audit and fix dynamic class construction before any visual QA.

## Technical Debt Patterns

Shortcuts that seem reasonable but create long-term problems.

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Hand-rolled MDX frontmatter parser | No extra dependency | Fails on multiline values, colons in strings, YAML arrays; silent errors during content updates | Only acceptable while frontmatter stays trivially simple (never add complex values) |
| Bare `JSON.parse()` without try-catch | Less code | Build/server crash with no helpful error message when any JSON file is malformed | Never — always wrap in try-catch |
| `console.log` of form submissions in production | Easy debugging during development | PII (names, emails) leaked to server logs; privacy concern | Never in production |
| Empty `next.config.ts` | No configuration overhead | No security headers, no CSP, no image domain allowlist; exposed to clickjacking, XSS, unoptimized images | Acceptable only while site has no images from external domains and no security requirements |
| FontAwesome full icon packs imported | Convenient during development | ~50KB+ added to JS bundle for unused icon variations | Acceptable for MVP; replace with explicit named imports once icon set stabilises |
| No error boundary (`error.tsx`) | Less boilerplate | Any component crash makes the entire page go white with no feedback | Never in production — add root-level error boundary before first deployment |

## Integration Gotchas

Common mistakes when connecting to external services.

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| Azure App Service (Node.js) | Using `Azure/static-web-apps-deploy` action from old Gatsby workflow | Use `azure/webapps-deploy` action with a zipped artifact containing `.next/`, `public/`, `package.json` |
| Azure App Service (Node.js) | Not setting startup command — App Service tries to serve `index.html` | Set startup command to `npm run start` in App Service Configuration blade |
| Azure App Service (Node.js) | Next.js default port (3000) conflicts with App Service expected port (8080) | Set `PORT=8080` in App Settings or use `next start -p 8080` in startup command |
| Resend email API | Committing `RESEND_API_KEY` to repo or `.env.production` | Add as App Service Application Setting; use `.env.example` to document variable name only |
| Resend email API | Not validating request body before calling Resend — crashes on missing fields | Add Zod schema validation server-side before any external API call |
| GitHub Actions | Referencing old `AZURE_STATIC_WEB_APPS_API_TOKEN_*` secret after switching to App Service | Create new secret `AZURE_WEBAPP_PUBLISH_PROFILE` from App Service Deployment Center |

## Performance Traps

Patterns that work at small scale but fail as usage grows.

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Synchronous `fs.readFileSync` for all content on every server request | Slow cold start; page generation time grows linearly with content files | Cache content at build time using `unstable_cache` or move to static generation; acceptable for current scale (<10 projects) | Noticeable at ~50+ content files or high traffic |
| Single IntersectionObserver per project component | Unnecessary observer instances; minor memory overhead | Use a single shared observer at the `Work` parent level, or use `react-intersection-observer` library | Noticeable at 30+ projects on a page |
| All projects rendered on a single page with no pagination | Slow initial load, long scroll distance | Add pagination or separate project routes when count grows | Visible degradation at ~20+ projects |
| No image optimisation config in `next.config.ts` | Full-size images served to all viewports; slow LCP | Enable `next/image` with explicit `domains` and `sizes` props; configure in `next.config.ts` | Immediately visible with current hero images if not already optimised |
| Dynamic Tailwind class construction (`.join()`, template literals) | Missing styles in production build | Use static complete class strings; use `clsx` for conditional composition | Breaks in first production build |

## Security Mistakes

Domain-specific security issues beyond general web security.

| Mistake | Risk | Prevention |
|---------|------|------------|
| No rate limiting on `/api/contact` | Endpoint can be flooded — spam submissions, DoS, cost amplification if email provider charges per send | Add rate limiting middleware (e.g., `@upstash/ratelimit` with Vercel KV, or a simple in-memory limiter for App Service) |
| `console.log` of contact form submissions (name, email, message) in production | PII in server logs; potential GDPR/privacy concern | Remove or gate behind `process.env.NODE_ENV === 'development'` check |
| No security headers in `next.config.ts` | Site vulnerable to clickjacking, XSS via iframes, MIME sniffing | Add `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, and a basic CSP to `next.config.ts` headers |
| `window.open(project.linkLive)` without URL validation | Project link data could contain `javascript:` URI — opens XSS vector | Validate URL with `new URL()` constructor; reject non-`http:`/`https:` protocols before calling `window.open()` |
| Stale Contentful credentials in `.env.*` files | Credentials for an unused service sitting on disk; risk if accidentally committed | Delete both `.env` files; create `.env.example` with only current required variable names |
| No CSRF protection on `/api/contact` | Cross-site request forgery — other sites can trigger form submissions on behalf of visitors | Add honeypot field; consider same-origin check via `Origin` or `Referer` header validation |

## UX Pitfalls

Common user experience mistakes in this domain.

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Contact form silently drops submissions (no email integration) | User believes they made contact; owner never knows | Wire up Resend before deploying; add explicit error state if API call fails |
| Form clears state on network error (existing bug) | User loses their typed message and must start over | Only clear form state on `res.ok === true`; on error, keep form values and show an error toast |
| `ButtonCta` is a `<div>` not a `<button>` | Keyboard users and screen reader users cannot interact with the primary CTA | Replace with `<button>` element; keyboard navigation and accessibility work for free |
| Modal allows body scroll on some browsers | User accidentally scrolls and interacts with background content | Add JS fallback: `document.body.style.overflow = 'hidden'` on modal open, restore on close |
| Stale content ("4+ years experience", 2023 bio) presents outdated professional story | Recruiters and collaborators see inaccurate seniority and experience level | Treat content refresh as blocking for any promotion of the URL; verify all numbers before first deployment |
| No OG image configured or OG image is outdated | Shared links on LinkedIn/Twitter show blank or wrong preview — first impression damage for a portfolio | Add a real OG image to `site-metadata.json`; verify it resolves to a real URL before announcing the site |

## Recovery Strategies

When pitfalls occur despite prevention, how to recover.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Contact form never delivered messages after going live | LOW | Add Resend integration, redeploy; notify anyone who may have submitted via alternative channel |
| Wrong workflow deployed to Static Web Apps instead of App Service | LOW | Delete Static Web Apps workflow, add App Service workflow, redeploy; no data loss |
| App Service shows blank page after deploy (wrong startup command) | LOW | Set startup command in App Service Configuration blade, restart; no redeploy needed |
| JSON content file malformed, crashing build | LOW | Fix JSON syntax error locally, verify with `npm run build`, push fix |
| Production CSS missing for dynamic Tailwind classes | MEDIUM | Audit dynamic class construction in all components, replace with static strings, redeploy |
| Contentful credentials accidentally committed to repo | HIGH | Immediately revoke credentials in Contentful dashboard, rotate, force-push rewritten history (requires coordinating with all contributors), audit access logs |
| PII in server logs reported as privacy issue | MEDIUM | Remove `console.log` in API route, redeploy; review what log retention policy App Service has and request deletion if needed |
